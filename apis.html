Security Architecture

All DigiLocker mobile APIs use JWT + AES-256-GCM encryption (NOT OAuth). Every request/response body is encrypted end-to-end.

Authentication Flow

1. Pre-login: No auth header. Body encrypted with AES-256-GCM (key: nativeAppCipher)
↓ (user signs in via mobile OTP / Aadhaar OTP / MPIN)
2. Login success: Server returns encrypted JWT access_token + refresh_token
↓
3. Post-login: Every request includes:
• Header: Authorization: Bearer <jwt_token>
• Header: device-security-id: <device_id>
• Body: AES-256-GCM encrypted JSON
↓ (on 401 response)
4. Token refresh: POST to authTokenRefresh with old access_token + refresh_token → new tokens → retry original request

Request/Response Encryption (AES-256-GCM)

AspectDetail
AlgorithmAES/GCM/NoPadding, 128-bit auth tag, 16-byte random nonce
Key derivationSHA-256(nativeAppCipher) → 32-byte AES key
Request encryptionplaintext JSON → encAesGcm256(json, key) → Base64 string (+ replaced with ---)
Response decryptionencrypted Base64 → decAesGcm256(body, key) → plaintext JSON
Integrity checkX-VALUE response header = SHA-256(decrypted_body)

HMAC Request Signing

HeaderValue
X-HMACHMAC-SHA256(secretKey, timestamp) — required on select endpoints
X-TSUnix timestamp in seconds (same value used to compute HMAC)

SSL Pinning & Network Clients

ClientComponentsUsed For
Pre-login clientSSL pinning only (no auth interceptor)Login, signup, OTP endpoints
Post-login clientAuthInterceptor + TokenAuthenticator + SSL pinningAll authenticated APIs

All 13 domains are pinned. AuthInterceptor adds Authorization + device-security-id headers automatically. TokenAuthenticator handles 401 → refresh → retry.

Offline Verification & Zero-Knowledge Proofs 2 interfaces

Local on-device proof generation + offline verification. Note: Credential issuance (create_credentials), key registration (send_vc_key_pair), and selective disclosure (verifiable_presentation) already exist in v2. What's NEW is the ability to verify credentials without network and generate ZK proofs (e.g., prove age>18 without revealing DOB).

What Already Exists in v2 (NOT new)

✅ create_credentials — Issue VC (JSON-LD) via acsapi.digilocker.gov.in/verifiable/1/credential
✅ create_credentials_jwt — Issue VC (JWT) via acsapi.digilocker.gov.in/verifiable/1.1/credential
✅ send_vc_key_pair — Register device public key via acsapi.digilocker.gov.in/verifiable/1/public-key
✅ verifiable_presentation — Create VP with selective disclosure via acsapi.digilocker.gov.in/verifiable/2/presentation
✅ verifiable_presentation_jwt — Create VP (JWT) via acsapi.digilocker.gov.in/verifiable/2.1/presentation
✅ SelectiveDisclosureActivity — User selects which fields to reveal, creates signed VP, presents via QR
✅ Local VC storage in Room DB (VCredentials entity)

What's NEW (doesn't exist in v2)

❌ Offline verification — v2 ALWAYS requires server for verification (verify_vc is a GET to vc.digilocker.gov.in). No peer-to-peer or NFC/BLE verification without internet.
❌ Zero-knowledge proofs — v2 reveals actual field values during selective disclosure. Cannot prove "age > 18" without revealing DOB, or "income > threshold" without revealing amount.
❌ Pre-provisioned verification keys — v2 has no key caching for offline use. Keys are always fetched live from server.
New Capability — Offline Verification Flow:
1. GET /api/v3/vc/verification-keys → pre-fetch & cache public keys on device (one-time, with ETag refresh)
2. generateProof(credential, challenge, selectedFields) → ZK proof generated locally [SDK — no network]
3. verifyProof(proof, cachedKeys, challenge) → boolean [SDK — fully offline, NFC/BLE/QR transfer]

Difference from v2:
• v2: User → creates VP via server API → gets QR with request_uri → verifier calls verify_vc on server
• NEW: User → generates proof locally → transfers via NFC/QR → verifier validates offline with cached keys
